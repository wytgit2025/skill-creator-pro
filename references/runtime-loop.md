# 运行期闭环（Runtime Loop）

> 这是 skill-creator-pro 的**第二层闭环**。SKILL.md 主流程（Loop A，开发期闭环）把技能从 0 做到"可交付"；本文档定义 **Loop B（运行期闭环）**，让技能上线后持续进化、且不跑偏。

---

## 1. 为什么需要这一层

交付不是终点。上线之后，**产品在变、平台在变、用户问法在变**，而静态技能没有反馈回路——它会停在交付第一天，让所有用户反复踩同一个坑，最后只能推倒重写。

Loop B 把"上线"变成起点：**每次调用留痕 → 巡检信号 → 人工确认改进 → 门禁再部署**，循环往复。

闭环只保证"在转"，**不保证"往对的方向转"**。所以本文档同时规定了防漂移机制（第 8 节）——飞轮越快，越需要方向盘和刹车。

---

## 2. 双闭环关系

```
Loop A（开发期 / build-time，已有）
  捕获意图 → 写初稿 → 跑 with-skill/基线 → benchmark + 人工评审
          → 迭代到满意 → 触发率优化 → 打包交付
                                        │
                                        ▼ （带 runtime 的技能交付即进入）
Loop B（运行期 / run-time，本文件）
  调用技能 → ①留痕 → ②巡检 → ③提改进【人确认】 → ④改 + 门禁 → 重新部署
     ▲                                                    │
     └────────────────────────────────────────────────────┘
```

Loop B 发现问题后，**"改 + 验证"直接复用 Loop A 的工具**（grader、aggregate_benchmark、quick_validate、eval-viewer），不另造一套。

---

## 3. 运行期闭环：四步

### 步骤 ① 留痕（每次调用，自动）

每次技能被调用，在任务结束（无论成功或失败）后执行留痕，向该技能的 `runtime/trace.jsonl` 追加一行：

```bash
python3 scripts/runtime_log.py --skill-root <技能根目录> \
  --status success \
  --input-summary "脱敏并截断的输入摘要" \
  --output-summary "脱敏并截断的输出摘要" \
  --duration-seconds 12.3 \
  [--feedback "用户反馈，可选"] [--error "错误摘要，失败时"] [--request-id "去重ID，可选"]
```

- 时间戳与技能版本号由脚本自动读取，无需手填。
- **失败安全**：留痕写不进只打印一条警告，**绝不能阻断或拖垮主任务**。
- 字段口径见第 5 节与 `references/schemas.md`。

### 步骤 ② 巡检（按节奏，见第 6 节）

复盘或定时触发时，读最近一个时间窗的 trace，聚合三类信号：

```bash
python3 scripts/scan_signals.py --skill-root <技能根目录> \
  --window-days 7 --out runtime/signals.md
```

产出 `runtime/signals.md`（人类可读待改清单）与 `runtime/signals.json`（结构化）。三类信号：
- **失败**：什么错误、多少次、影响多少个不同 request；
- **变慢**：超阈值次数、p50/p95 耗时、相对上一窗口的环比；
- **被批评**：用户负反馈 / 低评分条目聚类。

### 步骤 ②.5 沉淀经验（patterns/，不回滚）

巡检之后，把反复出现的模式固化成 `runtime/patterns/<slug>.md`：

```bash
python3 scripts/consolidate_patterns.py --skill-root <技能根目录>
```

- 脚本只做机械聚类和计数：跨 ≥3 个不同 request 反复出现的失败/批评才建页；已存在的只更新计数和时间戳。
- **根因和解法留空，由巡检 agent 或用户填**，脚本不猜。pattern 一旦建立，技能回滚了它也保留；改好后把状态从 `open` 标成 `mitigated`，历史计数不删。
- 巡检 agent 收尾时必须读所有 `open` pattern，补根因和建议，再连同 signals.md 一起交用户。这一步省了，经验就没沉淀下来。

### 步骤 ③ 提改进（必须人工确认）

- **先读 `runtime/change-log.md`**（若存在）：里面记着历次提案和裁决，跳过已被 rejected 的方向，别换个说法重复提。
- 只挑**跨多个 request 反复出现的普遍问题**，形成"建议改动清单"，先交给用户确认。
- **单条主观反馈（尤其"被批评"）不得直接驱动改动**——它可能只是个例或噪声。
- 改动遵循"通用原则优先，不叠个例补丁"，并先核对第 8 节的"使命与边界"锚点。

### 步骤 ④ 改 + 门禁 + 再部署

- 按确认结果修改技能，**版本号递增**，并在改动前留存当前版本快照。
- 跑第 7 节的回归门禁；**任何一维显著退化即否决**，不放行。
- 通过后重新部署，技能继续被调用，进入下一轮 Loop B。
- 部署后若发现问题，可用快照**回滚**到上一个确认版本。
- 无论提案被接受还是拒绝，巡检收尾时往 `runtime/change-log.md` 追加一行：日期、动了哪个文件、改了什么、回归结果、用户裁决。这是下一轮"先读历史"的数据来源。

## 4. 技能分型：要不要 runtime（不一刀切）

**需要 runtime（变化快、长期多人用）**
- 工作流型技能，强依赖外部网站 / 平台 / API（界面和接口会变）；
- 有多个用户、长期使用，问法多样；
- 出错代价较高、需要持续校准的技能。

**不需要 runtime（几乎不变、单一用途）**
- 纯确定性的小脚本（固定格式转换、确定性计算）；
- 一次性 / 单用户、用完即走的技能；
- 纯风格、主观表达类、无明确退化信号的技能。

拿不准时：若是一次性或单用户脚本，**先不加**；等看到它被反复使用、或同类问题第二次出现，再补（模块可增减，与 capability-modules 原则一致）。

---

## 5. 信号判定规则（默认阈值，可调）

- **失败**：`status=failure` 或存在 `error` 字段。
- **变慢**：满足任一即标记——
  - 单次耗时 > 阈值（默认 `--slow-threshold-sec`，未指定时取该技能历史 p95 的 1.5 倍）；
  - 本窗口 p95 较上一窗口上升 ≥ 50%（`--slow-regression 0.5`）。
- **被批评**：`feedback` 命中负向词（错、不对、慢、重做、又、怎么还是、别、误…）或为低评分。**噪声大，只作线索**。
- **最小样本保护**：窗口内样本 < 5 条时，只列原始记录，**不下"变慢 / 退化"结论**，避免小样本误判。

---

## 6. 巡检节奏

- **默认（推荐起步）**：手动 / 调用时触发——用户说"看看最近情况 / 复盘一下"，或技能被调用若干次后顺带巡检。
- **稳定后**：用定时任务（cron）按天 / 按周自动跑 `scan_signals.py`，把 signals 交给用户。
- 无论哪种，**"改"这一步永远需要人确认**，巡检自动化不等于改动自动化。

---

## 7. 门禁标准（回归不退化才放行）

1. **冻结金标准集**：在 `evals/golden.json` 维护一组**不参与改进、只用于回归打分**的用例（held-out）。它与开发用的 `evals/evals.json` 分开；修改金标准集必须用户确认，并据此重新基线化。
2. **多维否决**：每次改动后至少同时评估——
   - 断言通过率（金标准集）不下降；
   - 耗时不显著上升（p95 环比 ≤ 阈值）；
   - token 不显著膨胀；
   - 触发准确率不下降（可用 `evals/trigger_eval.json` 抽测）。
   **任一维显著退化即否决**，防止"刷好一个指标、牺牲其余"。
3. **保留基线**：回归始终包含 `without_skill`（新技能）或上一个确认版本（迭代中），确保技能没有越改越不如没有。
4. **独立打分**：由独立上下文的 grader / analyzer（最好与改技能者不同、必要时跨模型）评判，避免自己改自己评。
5. 回归命令复用：`quick_validate.py --deep` + `aggregate_benchmark.py`，需要时用 eval-viewer 给用户看。

---

## 8. 防漂移机制（核心）

自迭代技能存在五类典型跑偏：**目标漂移、过拟合、古德哈特定律（刷指标）、慢性回归、回声室 / 对新分布失能**。对应四道防线：

### 8.1 锚：使命与边界不变量
- 带 runtime 的技能，在 SKILL.md 顶部维护 `## 使命与边界（迭代不可改动）`：技能存在的目的、**绝不做的事**、成功的根本标准。
- 每轮改进先核对：**任何改动不得改变使命、不得突破边界**。
- 确需修改此区块 = 重新定义技能，必须用户**显式授权**，并视为新版本、重建基线。

### 8.2 方向盘：人确认 + 普遍性门槛
- 自动化止于"建议改动"；apply 必须人确认。
- 主观 / 单条反馈要看到跨 request、跨场景的**普遍性**才改；不追求对单个案例打补丁。
- 单轮改动**小步、有限范围**；动核心流程 / 删边界属高风险，需额外确认。

### 8.3 外部参照：金标准集 + 独立评判 + 跨模型
- 用冻结金标准集打分（第 7 节），杜绝"在练习题上越考越好"。
- 评估由独立子代理 / 不同模型完成，打破回声室；重要版本跨两档模型验证。
- 关注**输入分布漂移**：留意新型问题占比、兜底 / "无法处理"比例是否上升。

### 8.4 刹车：快照、回滚、熔断、定期回顾
- **快照 / 回滚**：每个确认版本留存，发现跑偏可回滚到上一稳定版。
- **趋势监测**：记录跨版本指标趋势（不只看当轮）；连续若干轮某指标缓慢下滑即报警，捕捉慢性退化。
- **熔断**：出现以下任一，立即停止迭代、交人工，并建议回滚——
  - 窗口失败率超过阈值（默认 30%）；
  - 某类错误 / 负反馈突增；
  - 金标准集通过率骤降；指标剧烈波动。
- **方向回顾**：每 N 轮（建议 5–10 轮）人工比对一次"技能当前行为 vs 最初使命"，并做一次精简（删除为个例加的、重复或矛盾的规则）。

> 诚实边界：以上机制能显著降低跑偏概率与代价，但无法在数学上根除——"对的方向"最终依赖人的判断。原则是**小步、可观测、可回滚、人握方向盘**。

---

## 9. 隐私与数据留存

- trace 的输入 / 输出只存**摘要**，默认截断长度，**敏感字段脱敏**；不记录密钥、凭据、个人敏感信息原文。
- 数据**默认只存本地**（技能自己的 `runtime/`），不外发、不上传。
- **真实 trace 不进入打包产物**（`package_skill.py` 已排除）。
- 可配置留存周期（到期清理）与一键关闭留痕；关闭后技能照常工作。

---

## 10. 老技能加装（retrofit）

对没带 runtime 的现有技能，按此加装：
1. 建 `runtime/`（放 `trace.jsonl`，初始为空 + 说明）；
2. 从 skill-creator-pro 复制 `runtime_log.py`、`scan_signals.py` 到该技能 `scripts/`（无则建）；
3. 在该技能 SKILL.md 加"运行期留痕"小节；建议同时补"使命与边界"区块；
4. （可选）建 `evals/golden.json` 金标准集；
5. 跑 `quick_validate.py --deep` 确认结构一致。

---

## 11. 平台升级路径

本层留痕与巡检目前是**指令式**的：靠运行技能的 agent 读 SKILL.md 后自觉执行，并非平台强制埋点，理论上可能漏记。
未来宿主平台（如豆包工作）若开放**官方线上 trace / 埋点 / 数据回流**：
- 用平台能力替换步骤 ①、② 的实现，做到强制、无遗漏；
- **方法、门禁、防漂移机制不变**，无需推倒重来。

---

## 12. 命令速查

```bash
# 留痕（每次调用后）
python3 scripts/runtime_log.py --skill-root <技能根> --status success \
  --input-summary "..." --output-summary "..." --duration-seconds 12.3

# 巡检（复盘 / 定时）
python3 scripts/scan_signals.py --skill-root <技能根> --window-days 7 \
  --out runtime/signals.md

# 沉淀经验（巡检后跑，把反复模式写进 runtime/patterns/）
python3 scripts/consolidate_patterns.py --skill-root <技能根>

# 门禁（改完，在 skill-creator-pro 根目录执行）
python3 -m scripts.quick_validate <技能根> --deep
python3 -m scripts.aggregate_benchmark <workspace>/iteration-N --skill-name <名>
```
