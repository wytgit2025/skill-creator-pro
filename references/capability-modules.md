# 技能能力模块：scripts / evals / runtime / 平台字段

判断一个技能要做哪些能力模块时看这份清单。**按结构属性判断，不按领域猜**——不给技能贴"轻量/重量"标签，那是二元分类，表达不了现实里的混合技能。

模块分两层：
- **交付前（build-time）**：`scripts`、`evals`、平台字段——决定技能"做得好不好"；
- **运行期（run-time）**：`runtime`——决定技能上线后"能不能持续进化"，与前三个正交、可叠加。

## 四个模块

| 能力模块 | 问自己 | 是 → |
|---|---|---|
| `scripts` | 有没有"每次都要做、输入输出确定、不需要临场判断"的操作？（格式转换、解析、校验、调固定 API） | 建 `scripts/` 目录，正文只说"遇到 X 就跑 scripts/xxx.py" |
| `evals` | 输出有没有**可客观验证**的对错？（文件生成没、数据提对没、字段全没） | 走完整 eval 闭环（带技能 + 基线、benchmark、触发率优化） |
| `runtime` | 上线后输入 / 平台 / 问法会不会持续变？会不会有多个用户长期使用？（工作流、外部网站 / API 依赖） | 建 `runtime/`，注入留痕 / 巡检脚本，走运行期闭环 |
| 平台字段 | 要不要分发到特定平台？（WorkBuddy / 千问等有专属元数据） | 加对应平台字段 |

**runtime 依赖 scripts。** 留痕 / 巡检脚本要放进 `scripts/`，所以选 `runtime` 会自动确保有 `scripts`（init 已处理）。

**别按领域猜。**「去 AI 味」不等于轻量——它可能有个确定性扫描脚本（那就建 `scripts/`）；「合同审查」不等于重量——它可能主要是判断、没有确定性操作。

## 交付前的四种常见组合（scripts × evals）

| scripts | evals | 例子 |
|:--:|:--:|---|
| ✗ | ✗ | 语气调整、写小说、海报风格包 |
| ✓ | ✗ | 去 AI 味（含扫描脚本）、固定格式输出 |
| ✗ | ✓ | 代码审查判断、风险识别 |
| ✓ | ✓ | PDF 转 Word、数据提取 |

**runtime 是否叠加**：表中任一种，只要"变化快、长期多人用、强外部依赖"就再加 runtime；纯确定性、单一用途、几乎不变的技能（如固定格式转换）不加。

## 两个原则

**判断就地做，不用声明。** 要不要这些模块，直接体现在「建不建对应目录」上——有 `scripts/` 就是有脚本，有 `evals/` 就是有测试，有 `runtime/` 就是有运行期闭环。**不要往 frontmatter 塞类型字段**（校验器看目录就够了，声明只会引入不一致）。

**模块可以迭代中增减。** 没做 `evals`、后来发现输出有客观对错 → 补上；做了 `scripts`、发现那个操作每次都不同 → 撤掉；技能上线后问题反复 → 加 `runtime`。别一次判死。

## 判定不确定时往哪偏

各模块证据强度不同，**不要整体往"完整"偏**——那等于把几个独立判断又捆回一个轴。

- **`scripts`：别猜。** 判据最硬（"每次都要做、输入输出确定"）。不确定就先不建，等迭代里看到同一个动作被重复写第二遍再补。
- **`evals`：这里要偏。** 判断型技能直接判 ✗ 容易整块放弃；但多数判断型输出是**部分可验证**的——周报文笔不可断言，"必须包含本周三个来源的条目"可断言。**把可验证的那部分抽出来做断言**。
- **`runtime`：按变化与规模判，一次性任务先不加。** 判据是"变化频率 × 用户规模 × 外部依赖"。不确定、且是一次性 / 单用户 / 纯确定性脚本时先不加，等看到它被反复使用、或同类问题第二次出现再补（多建的代价主要是每次调用多一步轻量留痕）。
- **平台字段：没有可偏的余地。** 纯需求问题（要不要分发到该平台）。

补 `scripts` 的判据不是"技能够不够完整"，而是"这个动作会不会被重复执行"：漏建脚本的代价是模型每次重写代码（慢、不稳、费 token），多建脚本的代价是一个不会被调用的死重量。两者不对称，但方向是前者。

## 看到用户这么说，就该想到哪个模块

判断表是抽象的，下面三个具体请求直接对应到模块，练几次直觉就有了：

| 用户原话 | 第一反应 | 为什么 |
|---|---|---|
| "帮我把这个 PDF 转一下方向 / 合并 / 抽表格" | **`scripts`**（pdfplumber/pypdf 片段直接进正文，长了再进 scripts/） | 每次都做、输入输出确定、不需要临场判断。OpenAI 原版叫 `rotate_pdf.py`，就是这种。 |
| "帮我做个 todo app / 一个看板" | **`assets/` 模板包**（不是 scripts） | 每次都要重写一样的 HTML/React 脚手架，这是"输出素材"不是"确定性计算"——模板复制进 assets/，不是写成脚本。 |
| "今天谁登录了 / 这张表里的 schema 是什么" | **`references/schema.md`**（不是 scripts） | 每次都要重新发现表结构和关系，把 schema 写进 references/，模型按需加载，不重。 |

这三类是最容易判错的：转 PDF 类容易漏 scripts，做 app 类容易把模板错塞进 scripts，查表类容易把 schema 错塞进正文。判据就一条——**这个东西是"每次跑都一样的计算"（scripts）、"每次输出都要复制的素材"（assets）、还是"每次要读一眼的说明"（references）**。

## 方案里要列的相关项

先定模块，再列相关项：

- 技能名、description 方向、调用方式、输入/输出格式、不做什么
- 要 `scripts` → 脚本怎么切、怎么调
- 要 `evals` → 几个测试用例、断言怎么设计
- 要 `runtime` → 留痕字段、巡检节奏、金标准集与门禁、使命与边界锚点（详见 `references/runtime-loop.md`）
- 要发多平台 → 补哪些平台字段
