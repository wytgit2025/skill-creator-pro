# 技能能力模块：scripts / evals / 平台字段

判断一个技能要做哪些能力模块时看这份清单。**按结构属性判断，不按领域猜**——不给技能贴"轻量/重量"标签，那是二元分类，表达不了现实里的混合技能。

## 三个模块

| 能力模块 | 问自己 | 是 → |
|---|---|---|
| `scripts` | 有没有"每次都要做、输入输出确定、不需要临场判断"的操作？（格式转换、解析、校验、调固定 API） | 建 `scripts/` 目录，正文只说"遇到 X 就跑 scripts/xxx.py" |
| `evals` | 输出有没有**可客观验证**的对错？（文件生成没、数据提对没、字段全没） | 走完整 eval 闭环（带技能 + 基线、benchmark、触发率优化） |
| 平台字段 | 要不要分发到特定平台？（WorkBuddy / 千问等有专属元数据） | 加对应平台字段 |

**别按领域猜。**「去 AI 味」不等于轻量——它可能有个确定性扫描脚本（那就建 `scripts/`）；「合同审查」不等于重量——它可能主要是判断、没有确定性操作。

## 四种常见组合

| scripts | evals | 例子 |
|:--:|:--:|---|
| ✗ | ✗ | 语气调整、写小说、海报风格包 |
| ✓ | ✗ | 去 AI 味（含扫描脚本）、固定格式输出 |
| ✗ | ✓ | 代码审查判断、风险识别 |
| ✓ | ✓ | PDF 转 Word、数据提取 |

## 两个原则

**判断就地做，不用声明。** 要不要这些模块，直接体现在「建不建对应目录」上——有 `scripts/` 就是有脚本，有 `evals/` 就是有测试。**不要往 frontmatter 塞类型字段**（校验器看目录就够了，声明只会引入不一致）。

**模块可以迭代中增减。** 没做 `evals`、后来发现输出有客观对错 → 补上；做了 `scripts`、发现那个操作每次都不同 → 撤掉。别一次判死。

## 判定不确定时往哪偏

三个模块证据强度不同，**不要整体往"完整"偏**——那等于把三个独立判断又捆回一个轴。

- **`scripts`：别猜。** 判据最硬（"每次都要做、输入输出确定"）。不确定就先不建，等迭代里看到同一个动作被重复写第二遍再补（模块可增减）。
- **`evals`：这里要偏。** 判据"有没有可客观验证的对错"容易被读成整块二选一——判断型技能直接判 ✗。但多数判断型输出是**部分可验证**的：周报的文笔不可断言，"必须包含本周三个来源的条目"可断言。**把可验证的那部分抽出来做断言**，别因为整体是判断型就整块放弃 eval。
- **平台字段：没有可偏的余地。** 纯需求问题（要不要分发到该平台）。

补 `scripts` 的判据不是"技能够不够完整"，而是"这个动作会不会被重复执行"：漏建脚本的代价是模型每次重写代码（慢、不稳、费 token），多建脚本的代价是一个不会被调用的死重量。两者不对称，但方向是前者。

## 方案里要列的相关项

先定模块，再列相关项：

- 技能名、description 方向、调用方式、输入/输出格式、不做什么
- 要 `scripts` → 脚本怎么切、怎么调
- 要 `evals` → 几个测试用例、断言怎么设计
- 要发多平台 → 补哪些平台字段
