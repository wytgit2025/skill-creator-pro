# 描述触发率优化

SKILL.md 前置元数据里的 `description` 字段，是决定模型会不会触发技能的最主要因素。创建或改进完技能之后，**主动提出优化描述**，提高触发准确率。

---

## 环境前提

动手前先确认当前环境支持哪种执行模式：

| 执行模式 | 需要什么 | 准确率预期 |
|---|---|---|
| 模式 A：脚本自动 | 有可编程调用的 agent 运行时（如 `claude -p`、`codebuddy -p`、`codex exec`、`openclaw agent exec`） | 85% - 95%+ |
| 模式 B：对话内手动 | 没有独立 CLI，但你自己就是模型 | 90%+ |
| 都做不到 | —— | **跳过并如实告诉用户"没跑"**，不要编造分数 |

**观测不到"技能被激活"的信号时，只能退化为哨兵探测，且此时测的是"执行了"而非"触发了"，语义不同，必须向用户讲明。**

---

## 第一步：生成触发测试用例

准备 20 个测试查询——一半应该触发，一半不应该触发。存成 JSON：

```json
[
  {"query": "用户的提示词", "should_trigger": true},
  {"query": "另一个提示词", "should_trigger": false}
]
```

这些查询必须是真实感的——像真用户会打出来的那种。不是抽象的请求，而是具体、有细节的。比如带文件路径、用户的工作背景、列名和数值、公司名、URL。带一点前因后果。有的可以是小写、有缩写、有错别字、口语化。长短混合，重点放在边界情况上，不要太一刀切（用户后面还有机会调整）。

差的例子："格式化这个数据"、"提取 PDF 文本"、"做个图表"

好的例子："ok 我老板刚发了个 xlsx 文件（在我下载文件夹里，叫什么'Q4 销售最终 FINAL v2.xlsx'），她让我加一列算利润率。收入应该在 C 列，成本在 D 列吧我记得"

**应该触发的查询（8-10 个）**：考虑覆盖面。同一意图的不同说法——正式的、口语的都要有。包括用户没有明确说出技能名或文件类型、但明显需要这个技能的情况。加一些不常见的用例，以及这个技能和其他技能竞争但应该赢的情况。

**不应该触发的查询（8-10 个）**：最有价值的是"近似干扰项"——和技能共享关键词或概念、但实际上需要别的东西的查询。想想相邻领域、含糊的表述（简单的关键词匹配会误触发），以及查询沾了技能的边但其实更适合别的工具的情况。

关键是：别把不应该触发的查询做得太明显不相关。比如对一个 PDF 技能来说，"写个斐波那契函数"这种负面测试太简单了——什么都测不出来。负面案例得是真的有迷惑性的。

---

## 第二步：和用户一起确认

把测试集拿给用户看，让他调整。用 HTML 页面方便编辑：

1. 从 `assets/eval_review.html` 读模板内容
2. 替换占位符：
   - `__EVAL_DATA_PLACEHOLDER__` → eval 项目的 JSON 数组（不要加引号——它是一个 JS 变量赋值）
   - `__SKILL_NAME_PLACEHOLDER__` → 技能的名字
   - `__SKILL_DESCRIPTION_PLACEHOLDER__` → 技能当前的描述
3. 写到临时文件里（比如 `/tmp/eval_review_<技能名>.html`），然后打开
4. 用户可以编辑查询、切换应不应该触发、增删条目，然后点 "Export Eval Set" 导出 JSON
5. 文件会下载到 `~/Downloads/eval_set.json`——如果有多个版本（比如 `eval_set (1).json`），取最新的那个

这一步很重要——垃圾测试用例 = 垃圾描述。

---

## 第三步：运行优化循环

根据你识别到的环境，选择对应的优化模式。**两种模式的严谨度完全一样**——只是执行者不同。

---

### 模式 A：脚本自动模式（有 CLI / API 配置的环境）

适用：Claude Code、OpenAI Codex、WorkBuddy、OpenClaw 等有原生 CLI 或 API 配置的环境

**告诉用户：** "这会花一些时间——我在后台跑优化循环，会定期跟你汇报进度。"

把 eval 集存到 workspace，然后在后台跑：

```bash
python -m scripts.run_loop \
  --eval-set <触发测试集的路径> \
  --skill-path <技能路径> \
  --model <当前会话用的模型 ID> \
  --max-iterations 5 \
  --verbose
```

**用当前会话的模型 ID**（从系统提示里拿）——这样触发测试的结果和用户实际体验一致。

**跑之前必须先跟用户讲清楚：这个脚本会在他的机器上起嵌套子进程。** 边界如下，两个开关默认都是关的，脚本在首次生效时会往 stderr 打一条明示提示：

| 项 | 默认行为 |
|---|---|
| 子进程 | 用平台原生 CLI（`claude -p`、`codebuddy -p` 等）逐条跑测试 query。子进程的提示词里含**技能 description**，而外部来源的技能 description 属于不可信文本——嵌套 agent 会读到它 |
| 自动确认（`-y`） | **默认不加**。只有显式给 `--allow-auto-approve`（或 `SKILL_CREATOR_ALLOW_AUTO_APPROVE=1`）才加，加了等于关掉该子进程的确认提示、它可以不经确认执行工具 |
| 宿主递归护栏 | **默认保留** `CLAUDECODE`。只给 `--allow-nested-claude`（或 `SKILL_CREATOR_ALLOW_NESTED_CLAUDE=1`）时才剔除，那等于绕过 Claude Code 的递归护栏 |
| 工作目录 | Claude 用项目根（要找 `.claude/commands`）；WorkBuddy 用新建的临时目录（`tempfile.mkdtemp`），跑完删除 |
| 落盘文件 | Claude 写 `<项目根>/.claude/commands/<技能>-test-<id>.md`；WorkBuddy 写 `~/.codebuddy/commands/<技能>-test-<id>.md`。都是临时文件，跑完即删（进程被强杀可能残留） |

**要开这两个开关就得先拿到用户同意**，别自己默默加上。另外，没开启自动确认时嵌套 CLI 可能停下来等确认，导致本次触发判定失真——出现这种情况要如实说明是"没跑成"，不能当成"没触发"。

**脚本内部做了什么：**
- 把 eval 集按 60% train / 40% held-out test 分割
- 评估当前描述（每个 query 跑 3 次，取可靠的触发率）
- 调模型根据失败案例提出改进建议
- 每个新描述在 train 和 test 上重新评估
- 最多迭代 5 次
- 最后选 test score 最高的描述（而不是 train score）——防止过拟合

**各平台触发测试方式差异（准确率预期）：**

| 平台 | 触发测试方式 | 准确率 |
|---|---|---|
| Claude | 原生端到端（临时 command 注入 + stream-json 解析） | 95%+ |
| WorkBuddy | 原生端到端（临时 command 注入 + stream-json 解析） | 95%+ |
| Codex | 任务中决策模式（注入 prompt + 输出标记检测） | 85%+ |
| OpenClaw | 任务中决策模式（注入 prompt + 输出标记检测） | 85%+ |
| 千问办公 | 对话内手动（无 CLI、无执行接口，走模式 B） | 90%+ |

跑的过程中，定期 tail 输出，告诉用户现在跑到第几轮了、分数怎么样。

---

### 模式 B：对话内手动模式（豆包工作 / 千问办公）

适用：豆包工作、千问办公这类没有可编程 CLI 的环境——你自己就是模型，不需要外部 API，直接在对话里完成整个优化循环。

**为什么是手动模式？** 豆包工作环境下没有独立的 `claude -p` 式 CLI，也没有对外暴露的模型 API Key；千问办公同理，它的企业版 OpenAPI 只有技能资产管理接口、没有执行任务的接口。但没关系——**你自己就是那个模型**。脚本版做的所有事，你在对话里都能做，而且更直接。

**完整步骤：**

**Step 1：拆分 train / test 集**

把你刚才和用户确认的 20 个测试查询，按 60% 训练 / 40% 测试拆分。分层拆分——正例和反例各自按比例分，不要随机混着分。

- 训练集：用来迭代改进描述
- 测试集：留着做最终评选，**改进阶段绝对不能看测试集的结果**——防止过拟合

**Step 2：评估当前描述**

对训练集里的每个查询，你自己判断：
> "如果用户发来这个查询，加上当前技能的描述，我会不会决定调用这个技能？"

判断标准要严格，要模拟真实场景：
- 想象技能列表里还有其他类似的技能
- 想象用户的查询是口语化、有上下文的
- 不要因为描述里有关键词就触发——要判断这个查询是不是真的需要这个技能的专业能力
- 简单的一步任务（读个文件、写个简单文本）就算描述匹配也不触发

每个查询判断 3 次，取触发率（3 次里有几次你觉得会触发）。触发率 >= 0.5 就算"通过"（该触发的查询），< 0.5 就算"通过"（不该触发的查询）。

**把结果记录下来，格式如下：**

```
第 1 轮评估结果：
- 该触发但没触发（漏触发）：X 个
  - "查询 1"（触发率 1/3）
  - "查询 2"（触发率 0/3）
- 不该触发却触发了（误触发）：X 个
  - "查询 3"（触发率 3/3）
  - "查询 4"（触发率 2/3）
- 总通过率：X/训练集总数
```

**Step 3：改进描述**

根据失败案例，写一个新的描述版本。改进时注意：
- **不要过拟合到眼前这几个案例**——从失败中提炼更宽泛的用户意图类别
- 不要写成一长串"应该触发 X、Y、Z"的列表
- 用祈使句开头
- 聚焦用户意图，不是技能实现
- 控制在 100-200 词，不超过 1024 字符硬上限

**如果新描述超了 1024 字符，自己压缩一下**——保留最重要的触发词和意图覆盖。

**Step 4：重跑评估**

用新描述，再对训练集做一轮评估（同样每个查询判断 3 次）。记录新的通过率。

**Step 5：循环**

重复 Step 3-4，最多 5 轮。每一轮都记录：
- 第几轮
- 描述内容
- 训练集得分

**Step 6：选最优**

迭代完之后，拿历史上每一轮的描述，去跑**测试集**（之前留出来的那 40%）。**测试集只用来选最优，不用来改进**。

选测试集得分最高的那个描述版本——而不是训练集得分最高的。这是为了防止过拟合。

**Step 7：汇报结果**

给用户看：
- 每一轮的描述和训练集得分
- 测试集最终得分
- 你选了哪个版本，为什么
- 修改前后的对比

---

## 优化描述的技巧（两种模式通用）

- 用祈使句开头——"使用此技能进行..."而不是"这个技能做..."
- 聚焦用户的意图，而不是技能怎么实现
- 描述要和其他技能区分开，有辨识度
- 不要写成一长串"应该触发 X、Y、Z"的列表——那是过拟合，应该提炼成更宽泛的意图类别
- 控制在 100-200 词左右（一般硬上限是 1024 字符）

---

## 技能触发的原理

理解触发机制有助于设计更好的测试查询。技能是以"名称 + 描述"的形式出现在模型的可用技能列表里的，模型根据描述来决定要不要调用。重要的是：**模型只会对它搞不定的复杂任务才去查技能**——像"读这个 PDF"这种一步就能搞定的简单查询，就算描述完美匹配，也可能不触发，因为模型用基础工具直接就干了。复杂的、多步骤的、专业领域的查询，才会可靠地触发技能。

这意味着你的测试查询得有足够的"分量"，确实需要借助技能才能做好。像"读文件 X"这种简单查询就是糟糕的测试用例——描述写得再好也不触发。

---

## 第四步：应用优化结果

把优化后的新描述更新到 SKILL.md 的前置元数据里。给用户看修改前后的对比，报告分数。
