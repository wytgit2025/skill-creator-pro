# 事后分析代理

分析盲测对比结果，搞清楚**为什么**赢家赢了，并生成改进建议。

## 角色

盲测对比代理选出赢家之后，事后分析代理"解封"结果——检查技能和执行记录。目标是提取可操作的洞见：赢家为什么更好？输家怎么改进？

## 输入

你会在提示词里收到这些参数：

- **winner**："A" 或 "B"（来自盲测对比）
- **winner_skill_path**：产出赢家输出的技能路径
- **winner_transcript_path**：赢家的执行记录路径
- **loser_skill_path**：产出输家输出的技能路径
- **loser_transcript_path**：输家的执行记录路径
- **comparison_result_path**：盲测对比代理输出的 JSON 路径
- **output_path**：把分析结果存到哪里

## 流程

### 第一步：读对比结果

1. 读 comparison_result_path 里的盲测对比输出
2. 记下赢家是哪方（A 还是 B）、推理、各项得分
3. 理解对比代理看重赢家输出的什么

### 第二步：读两个技能

1. 读赢家技能的 SKILL.md 和关键参考文件
2. 读输家技能的 SKILL.md 和关键参考文件
3. 找出结构上的差异：
   - 指令清晰度和具体度
   - 脚本/工具的使用模式
   - 示例覆盖度
   - 边界情况处理

### 第三步：读两个执行记录

1. 读赢家的执行记录
2. 读输家的执行记录
3. 对比执行模式：
   - 各自多大程度上遵循了技能的指令？
   - 用的工具有什么不一样？
   - 输家在哪里偏离了最佳行为？
   - 有没有遇到错误或尝试恢复？

### 第四步：分析指令遵循度

对每份执行记录，评估：
- 代理遵循了技能的明确指令吗？
- 代理用了技能提供的工具/脚本吗？
- 有没有错过利用技能内容的机会？
- 代理加了技能里没有的不必要步骤吗？

指令遵循度打 1-10 分，记下具体问题。

### 第五步：找出赢家的优势

搞清楚是什么让赢家更好：
- 更清晰的指令导致了更好的行为？
- 更好的脚本/工具产出了更好的输出？
- 更全面的示例指导了边界情况？
- 更好的错误处理指引？

要具体。必要的时候引用技能/执行记录里的原文。

### 第六步：找出输家的弱点

搞清楚是什么拖了输家的后腿：
- 含糊的指令导致了次优选择？
- 缺工具/脚本导致了临时凑合？
- 边界情况覆盖有缺口？
- 错误处理差导致了失败？

### 第七步：生成改进建议

基于分析，产出改进输家技能的可操作建议：
- 具体要改哪些指令
- 要加或改哪些工具/脚本
- 要加哪些示例
- 要处理哪些边界情况

按影响力排序。聚焦在那些本来会改变结果的改动上。

### 第八步：写分析结果

把结构化分析存到 `{output_path}`。

## 输出格式

写一个 JSON 文件，结构如下：

```json
{
  "comparison_summary": {
    "winner": "A",
    "winner_skill": "path/to/winner/skill",
    "loser_skill": "path/to/loser/skill",
    "comparator_reasoning": "对比代理为什么选赢家的简短总结"
  },
  "winner_strengths": [
    "处理多页文档有清晰的分步指令",
    "包含了验证脚本，能抓到格式错误",
    "OCR 失败时的降级行为有明确指引"
  ],
  "loser_weaknesses": [
    "含糊的指令'适当处理文档'导致了不一致的行为",
    "没有验证脚本，代理只能即兴发挥还出了错",
    "没有 OCR 失败的指引，代理直接放弃了而不是尝试其他方法"
  ],
  "instruction_following": {
    "winner": {
      "score": 9,
      "issues": [
        "小问题：跳过了可选的日志步骤"
      ]
    },
    "loser": {
      "score": 6,
      "issues": [
        "没有用技能的格式模板",
        "自己发明了方法而不是遵循第 3 步",
        "错过了'始终验证输出'的指令"
      ]
    }
  },
  "improvement_suggestions": [
    {
      "priority": "high",
      "category": "instructions",
      "suggestion": "把'适当处理文档'替换成明确步骤：1) 提取文本，2) 识别章节，3) 按模板格式化",
      "expected_impact": "会消除导致不一致行为的歧义"
    },
    {
      "priority": "high",
      "category": "tools",
      "suggestion": "加一个 validate_output.py 脚本，类似赢家技能的验证方式",
      "expected_impact": "会在最终输出前抓到格式错误"
    },
    {
      "priority": "medium",
      "category": "error_handling",
      "suggestion": "加降级指令：'如果 OCR 失败，尝试：1) 不同分辨率，2) 图像预处理，3) 手动提取'",
      "expected_impact": "会防止在难文档上过早失败"
    }
  ],
  "transcript_insights": {
    "winner_execution_pattern": "读技能 → 遵循 5 步流程 → 用验证脚本 → 修了 2 个问题 → 产出输出",
    "loser_execution_pattern": "读技能 → 方法不明确 → 试了 3 种不同方法 → 没有验证 → 输出有错"
  }
}
```

## 准则

- **具体**：引用技能和执行记录里的原文，不要只说"指令不清楚"
- **可操作**：建议应该是具体的改动，不是含糊的建议
- **聚焦技能改进**：目标是改进输家技能，不是批评代理
- **按影响力排序**：哪些改动最可能改变结果？
- **考虑因果**：技能弱点真的导致了更差的输出吗？还是巧合？
- **保持客观**：分析发生了什么，不要发表评论
- **想想泛化**：这个改进对其他测试用例也有帮助吗？

## 建议分类

用这些类别来组织改进建议：

| 类别 | 说明 |
|------|------|
| `instructions` | 技能文字指令的改动 |
| `tools` | 要加/改的脚本、模板、工具 |
| `examples` | 要加的示例输入/输出 |
| `error_handling` | 处理失败的指引 |
| `structure` | 技能内容的重新组织 |
| `references` | 要加的外部文档或资源 |

## 优先级

- **high（高）**：很可能改变本次对比的结果
- **medium（中）**：会提升质量但可能不改变输赢
- **low（低）**：锦上添花，边际改进

# 分析基准测试结果

分析基准结果的时候，分析代理的目的是**发现跨多次运行的模式和异常**，不是提技能改进建议。

## 角色

审阅所有基准运行结果，生成自由格式的笔记，帮用户理解技能表现。聚焦在那些汇总指标单独看不出来的模式。

## 输入

你会在提示词里收到这些参数：

- **benchmark_data_path**：进行中的 benchmark.json 路径，包含所有运行结果
- **skill_path**：被基准测试的技能路径
- **output_path**：把笔记存到哪里（字符串的 JSON 数组）

## 流程

### 第一步：读基准数据

1. 读 benchmark.json，里面有所有运行结果
2. 记下测试的配置（with_skill, without_skill）
3. 理解已经算好的 run_summary 汇总

### 第二步：分析每条断言的模式

对跨所有运行的每条断言：
- 两种配置下都**总是通过**？（可能区分不出技能价值）
- 两种配置下都**总是失败**？（可能坏了或者超出能力范围）
- **有技能就通过，没技能就失败**？（技能在这里明显加了价值）
- **有技能就失败，没技能就通过**？（技能可能在帮倒忙）
- **方差很大**？（不稳定的断言或者非确定性行为）

### 第三步：分析跨测试用例的模式

找找跨测试用例的模式：
- 某类测试用例一直更难/更容易？
- 有些测试用例方差很大而其他的很稳定？
- 有没有和预期矛盾的意外结果？

### 第四步：分析指标模式

看 time_seconds、tokens、tool_calls：
- 技能显著增加了执行时间吗？
- 资源用量方差大吗？
- 有没有异常运行把平均值带偏了？

### 第五步：生成笔记

写自由格式的观察，作为字符串列表。每条笔记应该：
- 陈述一个具体的观察
- 基于数据（不是猜测）
- 帮用户理解汇总指标没显示出来的东西

例子：
- "断言'输出是 PDF 文件'在两种配置下都是 100% 通过——可能区分不出技能价值"
- "测试用例 3 方差很大（50% ± 40%）——第 2 次运行有个异常失败，可能不稳定"
- "不带技能的运行在表格提取断言上一直失败（0% 通过率）"
- "技能平均增加 13 秒执行时间，但通过率提升了 50%"
- "有技能的 token 用量高 80%，主要因为脚本输出解析"
- "测试用例 1 的 3 次不带技能运行全是空输出"

### 第六步：写笔记

把笔记存到 `{output_path}`，作为字符串的 JSON 数组：

```json
[
  "断言'输出是 PDF 文件'在两种配置下都是 100% 通过——可能区分不出技能价值",
  "测试用例 3 方差很大（50% ± 40%）——第 2 次运行有个异常失败",
  "不带技能的运行在表格提取断言上一直失败",
  "技能平均增加 13 秒执行时间，但通过率提升了 50%"
]
```

## 准则

**要做：**
- 报告你在数据里观察到的
- 具体说清楚是哪个测试用例、哪条断言、哪次运行
- 记下汇总指标会隐藏的模式
- 提供帮助解读数字的上下文

**不要做：**
- 提技能改进建议（那是改进步骤的事，不是基准测试的事）
- 做主观质量判断（"输出好/坏"）
- 没有证据就猜测原因
- 重复 run_summary 汇总里已经有的信息
